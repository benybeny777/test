# TASKS.md — 未完了作業と着手順

実装を担当する作業エージェント（Codex を想定）向けの指示書。**上から順に着手する。** 順序には理由があり、後述の「なぜこの順か」を読んでから始めること。

着手前に必ず読む: [AGENTS.md](../AGENTS.md)（恒久ルール） → [SPEC.md](../SPEC.md)（現行仕様） → [REVERSE.md](REVERSE.md)（本家の実測仕様）。

各タスクは**1タスク = 1 PR**とする。完了したらこのファイルの該当項目を消し、結論を `SPEC.md` へ移す。

## なぜこの順か

このプロジェクトには**成立するかどうか未検証の技術リスクが2つ**ある。

1. **表情のローカル生成**（T2）— 本家はクラウドの汎用画像編集モデルで「同一性・向き・画風を保ったまま表情だけ変える」をやっていた。ローカル拡散モデルで同等が出せるかは未検証。
2. **フェイスパッチ逆投影**（T3）— 幾何計算なので理屈上は確実だが、AI生成メッシュの汚いUVで実際に破綻しないかは未検証。

**この2つが成立しなければ製品が成立しない。** だからアプリの外枠より先に、この2つを最小構成で検証する。逆に、ここさえ通れば残りは既知の作業になる。

画像→3D（T5）とリギング（T6）は後回しでよい。**既存の VRM / GLB を手で用意すれば T2・T3 は検証できる**ためで、リスクの高い方から潰す。

**完了条件**: `cargo xtask dev` でウィンドウが出る。`cargo test --lib` が通る。

## T2. 表情のローカル生成（技術リスク最大。最優先で検証する）

**目的**: 顔画像1枚から、同一性を保ったまま表情差分と母音口形を作れるかを確かめる。

まだ Tauri へ組み込まない。**`xtask` のサブコマンドか単体の検証バイナリで、画像を入れて画像が出るところまで**を作る。UI は不要。

入力: 顔正面のキャプチャ画像 1枚（1024x1024 RGBA）
出力: `smile / blink / angry / sad / surprised / mouth_open` の6表情 ＋ 各表情の `a/i/u/e/o/close` 6母音

**バックエンドは ComfyUI で確定**（[SPEC.md](../SPEC.md) 4.7.2）。同梱して本アプリ管理下で起動し、**開発機の手元 ComfyUI に依存する実装にしない**。ワークフローは JSON でリポジトリ管理する。初期構成は標準ノードだけを使い、カスタムノードが必要になった場合はライセンス監査後の固定版だけを同梱する。

実装方針（[SPEC.md](../SPEC.md) 4.7.1）:

1. **顔領域のインペイントに限定する。** 画像全体を再生成しない。マスク外は原理的に変わらない
2. **denoise を低く**（0.3〜0.45目安）して構造を保つ
3. **ControlNet（lineart / depth / softedge）で輪郭を拘束する**
4. プロンプトは**維持すべき属性の明示**（同一性・向き・髪型・色・ライティング・画風）と**左右反転の禁止**を含める。本家の英語プロンプト文言を写さず、独自に書く

品質が届かない場合は [SPEC.md](../SPEC.md) 4.7.3 の段階表を**上から順に**踏む。**段階を飛ばして外部サービスを提案しない。** 特に**段階7（外部生成画像のインポート導線）は製品の前提を1つも緩めずに品質を得られる**ため、段階9（アプリからクラウドを呼ぶ）より先に必ず検討する。

**検証**: 生成結果を中立画像と並べて目視し、以下を確認する。

- 左右が反転していないか
- 髪型・服・アクセサリ・色が変わっていないか
- 顔の位置とサイズがずれていないか
- 母音の口形が実際に区別できるか（特に `i` と `e`、`u` と `o`）

**完了条件**: 上記4点を満たす結果が、少なくとも3体の異なるキャラで安定して出ること。目視確認の判断は利用者に委ねてよいが、**中立画像との差分画素率**を数値で出して PR 本文へ載せる。

**停止条件**: どう調整しても左右反転や画風ドリフトが止まらない場合は、そこで止めて利用者へ報告する。[AGENTS.md](../AGENTS.md)「ローカルで成立しないと判明した場合」に従い、**実測値・試した緩和策・クラウドを使う場合の具体案（工程・概算費用・利用者に必要な手続き・失うもの）・使わない代替案（表情ごとのLoRA、顔パーツ差し替え、手描きテンプレート、機能削減）を揃えて出す。判断は利用者が行う。** 勝手にクラウドを入れない。勝手に機能を削らない。

## T3. フェイスパッチ逆投影（本実装の中核）

**目的**: T2 の出力を、実際に3Dモデルのテクスチャへ焼き戻せることを確かめる。

これも Tauri へ組み込む前に、**単体で完結する検証経路**として作る。仕様は [SPEC.md](../SPEC.md) 4.4 に全部書いてある。本家の実測パラメータは [REVERSE.md](REVERSE.md) を参照する。

入力: リグ付きモデル（VRM / GLB）＋ 中立キャプチャ ＋ 表情キャプチャ
出力: 投影済み UV アトラス（2048x2048 PNG）

実装の要点（省略すると必ず破綻する）:

- **中立時のスキニング済みメッシュをスナップショットとして保持し、投影は必ずそれを使う。** 現在ポーズで投影すると、ポーズが変わるたび結果がずれる
- **頭ボーンのウェイト閾値で三角形を絞る。** これをやらないと体や髪の裏側にも顔が焼かれる
- **レイキャストで最前面判定する。** やらないと後頭部へ顔が貫通する。深度窓の内側の最前面ヒットだけ採用する
- **中立との差分マスクで書き込みを限定する。** これが画像生成のドリフトに対する最後の防波堤になる（[SPEC.md](../SPEC.md) 4.7.1）
- **UV継ぎ目を数px膨張させる。** ただし非採用三角形のUV領域を避けて膨張させる。避けないと他パーツへ滲む
- **書き込み画素が0なら失敗として明示エラー**にし、診断画像（採用三角形マスク・元画像マスク・書き込み領域）を保存する

**検証**:

- 既知のメッシュと既知の編集画像で、**投影画素数と書き込み領域のバウンディングボックス**をゴールデン値と比較するテストを置く
- 実際にモデルへ適用して three.js で表示し、顔が正しい位置に貼られているか目視する
- 意図的にずれた画像を入れて、差分マスクが効いて破綻を吸収するか確認する

**完了条件**: 6表情 × 6母音 = 36枚の投影が生成でき、three.js 上で表情が切り替わって見えること。

## T4. リップシンクと OBS 出力

T2・T3 が通れば、ここは既知の作業になる。

### T4a. リップシンク

[SPEC.md](../SPEC.md) 4.5 の通り実装する。本家の実測アルゴリズムは [REVERSE.md](REVERSE.md)。

- Rust 側（`cpal` + `rustfft`）で解析する。**ブラウザ側で二重に解析しない**
- 本家は O(N²) の素朴な DFT だった。**FFT へ置き換える**
- フォルマント値・閾値・平滑化フレーム数はすべて設定から読む（ハードコードしない）
- VAD で発話区間を切り出し、whisper.cpp へ渡せる形にする

**検証**: 合成した母音音声（既知のフォルマント）を流し、判定結果が期待通りかをテストする。実マイクでの確認は最後に1回でよい。

### T4b. OBS 出力

[SPEC.md](../SPEC.md) 4.6 の通り、**透過ブラウザソース直描画**で実装する。MJPEG にしない。

- ローカル HTTP サーバが `ui-stream/` を配信し、WebSocket で状態（表情キー・口形キー・ポーズ・構図）だけを送る
- `ui/` と `ui-stream/` は three.js の描画コードを `ui/shared/` で共有する。**二重実装しない**
- ポートは範囲を順に試し、全滅したら明示エラー
- 有効状態を設定へ永続化し、次回起動で復帰する

**検証**: 実ブラウザで透過描画されること、WebSocket の状態更新が反映されることを確認する。OBS 実機での確認は利用者に委ねてよい。

**この時点で `docs/REVERSE.md` の「リップシンク」「OBS 連携」節を削除できる。**（[AGENTS.md](../AGENTS.md) のリバース資料の扱い）

## T5. 画像→3D 生成

T0 の結論に従ってモデルを選定し、Python サイドカーとして実装する。

- 起動は Rust の `sidecar` モジュールから**単発プロセス**で行い、入出力はファイルパスと JSON 1行。常駐サーバにしない
- 進捗は stdout の JSON Lines で流し、Rust が UI へ中継する
- **子プロセスは `kill` して `wait` でハンドルまで回収する**
- **CUDA 対応 NVIDIA GPU を検出できた場合だけ CUDA wheel を取得する。** GPU 非搭載環境ではこの機能を明示的に非対応とし、CPU で何十分も待たせない
- 背景除去（`rembg` isnet-anime）を前段に置く
- **生成は A ポーズ相当に正規化して出す**（T6 の前提になる）
- Python 3.12 ランタイムを同梱し、利用者に Python のインストールを要求しない

**検証**: VRAM 8GB の実機で実際に生成が完走すること。所要時間とピーク VRAM を実測して PR 本文へ書く。

## T6. リギング

[SPEC.md](../SPEC.md) 4.3 の**テンプレートヒューマノイド適合＋自動スキニング**で実装する。学習ベースの自動リグ（UniRig 等）は却下済み。理由は SPEC の比較表を参照。

- メッシュの寸法から VRM 標準ヒューマノイドボーンを配置する
- スキニングウェイトは heat diffusion 系の自動ウェイトで算出する
- 出力は **VRM**（ヒューマノイド互換）
- **A/T ポーズ以外の入力は検出して明示エラーにする。** 黙って崩れたモデルを出さない

**未確定**: heat diffusion 自動ウェイトの実装手段（自前 / Blender 同梱して `bpy` / 既存ライブラリ）。**Blender 同梱は配布サイズが数百MB増えるため、まず自前実装の実現性を検証してから決める。** 結論を `SPEC.md` 4.3 へ書く。

**検証**: 生成モデルの標準ヒューマノイドボーンが全て存在し、想定範囲の位置にあることをテストする。実際にアイドルアニメーションを流して破綻しないか目視する。

## T6.5. 先行製品を上回る改良（[SPEC.md](../SPEC.md) 4.10）

**方針は利用者承認済み。制約内（クラウド不使用・VRAM 8GB）で成立するなら実装する。** 制約と衝突したら本体機能を優先し、見送った案と理由を記録する。

着手条件は T3 完了（投影の領域分離が実際に効くか見てから判断するため）。

- **A. 表情と母音の直交化** — 目・眉の差分（N枚）と口の差分（6枚）を分離して投影時に合成し、生成枚数を **7N → N+6** へ減らす。**効果が最も大きい。** リスクは不自然な組み合わせ（悲しい目＋大きく開いた口）。表情ごとに口の開き量を制限する係数で緩和する
- **B. 表情遷移のクロスフェード** — 投影済みテクスチャ間を補間する。実装コストは低い
- **C. 自動まばたき・アイドル揺れ** — `blink` テクスチャをランダム間隔で差し込む。頭・体の微小な揺れを手続き的に足す
- **D. 外部生成画像のインポート導線** — **優先度高。T2の結果次第では T2 の直後に着手する。** 投影前の1024px画像を外部で作って持ち込めるようにする。**製品はクラウドを呼ばないまま品質問題を解決できる出口**（[SPEC.md](../SPEC.md) 4.10 D、4.7.3 段階7）。中立キャプチャの書き出し、投入画像の位置ずれ・左右反転・色差の検出と警告、キャッシュ署名への反映まで含む
