## なぜこの順か

このプロジェクトには、当初**成立するかどうか未検証の技術リスクが2つ**あった。T2の表情ローカル生成とT3のフェイスパッチ逆投影は、女性3体で成立を確認済みである。

1. **表情のローカル生成**（T2）— 本家はクラウドの汎用画像編集モデルで「同一性・向き・画風を保ったまま表情だけ変える」をやっていた。ローカル拡散モデルで同等が出せるかは未検証。
2. **フェイスパッチ逆投影**（T3）— 既知のリグ付きメッシュと女性3体・各36枚で、最前面判定、差分マスク、UV継ぎ目処理、three.js表示まで成立を確認済み。

**この2つが成立しなければ製品が成立しない。** アプリ統合より先に最小構成で検証し、両方が通ったため、以降は依存順に既知の作業を進める。

次はリアルタイム動作に必要なリップシンクとOBS出力を固め、その後に画像→3D（T5）とリギング（T6）を接続する。

## T4. リップシンクと OBS 出力

T2・T3 が通れば、ここは既知の作業になる。

### T4a. リップシンク

[SPEC.md](../SPEC.md) 4.5 の通り実装する。本家の実測アルゴリズムは [REVERSE.md](REVERSE.md)。

- Rust 側（`cpal` + `rustfft`）で解析する。**ブラウザ側で二重に解析しない**
- 本家は O(N²) の素朴な DFT だった。**FFT へ置き換える**
- フォルマント値・閾値・平滑化フレーム数はすべて設定から読む（ハードコードしない）
- VAD で発話区間を切り出し、whisper.cpp へ渡せる形にする

**検証**: 合成した母音音声（既知のフォルマント）を流し、判定結果が期待通りかをテストする。実マイクでの確認は最後に1回でよい。

### T4b. OBS 出力

[SPEC.md](../SPEC.md) 4.6 の通り、**透過ブラウザソース直描画**で実装する。MJPEG にしない。

- ローカル HTTP サーバが `ui-stream/` を配信し、WebSocket で状態（表情キー・口形キー・ポーズ・構図）だけを送る
- `ui/` と `ui-stream/` は three.js の描画コードを `ui/shared/` で共有する。**二重実装しない**
- ポートは範囲を順に試し、全滅したら明示エラー
- 有効状態を設定へ永続化し、次回起動で復帰する

**検証**: 実ブラウザで透過描画されること、WebSocket の状態更新が反映されることを確認する。OBS 実機での確認は利用者に委ねてよい。

**この時点で `docs/REVERSE.md` の「リップシンク」「OBS 連携」節を削除できる。**（[AGENTS.md](../AGENTS.md) のリバース資料の扱い）

## T5. 画像→3D 生成

T0 の結論に従ってモデルを選定し、Python サイドカーとして実装する。

- 起動は Rust の `sidecar` モジュールから**単発プロセス**で行い、入出力はファイルパスと JSON 1行。常駐サーバにしない
- 進捗は stdout の JSON Lines で流し、Rust が UI へ中継する
- **子プロセスは `kill` して `wait` でハンドルまで回収する**
- **CUDA 対応 NVIDIA GPU を検出できた場合だけ CUDA wheel を取得する。** GPU 非搭載環境ではこの機能を明示的に非対応とし、CPU で何十分も待たせない
- 背景除去（`rembg` isnet-anime）を前段に置く
- **生成は A ポーズ相当に正規化して出す**（T6 の前提になる）
- Python 3.12 ランタイムを同梱し、利用者に Python のインストールを要求しない

**検証**: VRAM 8GB の実機で実際に生成が完走すること。所要時間とピーク VRAM を実測して PR 本文へ書く。

## T6. リギング

[SPEC.md](../SPEC.md) 4.3 の**テンプレートヒューマノイド適合＋自動スキニング**で実装する。学習ベースの自動リグ（UniRig 等）は却下済み。理由は SPEC の比較表を参照。

- メッシュの寸法から VRM 標準ヒューマノイドボーンを配置する
- スキニングウェイトは heat diffusion 系の自動ウェイトで算出する
- 出力は **VRM**（ヒューマノイド互換）
- **A/T ポーズ以外の入力は検出して明示エラーにする。** 黙って崩れたモデルを出さない

**未確定**: heat diffusion 自動ウェイトの実装手段（自前 / Blender 同梱して `bpy` / 既存ライブラリ）。**Blender 同梱は配布サイズが数百MB増えるため、まず自前実装の実現性を検証してから決める。** 結論を `SPEC.md` 4.3 へ書く。

**検証**: 生成モデルの標準ヒューマノイドボーンが全て存在し、想定範囲の位置にあることをテストする。実際にアイドルアニメーションを流して破綻しないか目視する。

## T6.5. 先行製品を上回る改良（[SPEC.md](../SPEC.md) 4.10）

**方針は利用者承認済み。制約内（クラウド不使用・VRAM 8GB）で成立するなら実装する。** 制約と衝突したら本体機能を優先し、見送った案と理由を記録する。

着手条件は T3 完了（投影の領域分離が実際に効くか見てから判断するため）。

- **A. 表情と母音の直交化** — 目・眉の差分（N枚）と口の差分（6枚）を分離して投影時に合成し、生成枚数を **7N → N+6** へ減らす。**効果が最も大きい。** リスクは不自然な組み合わせ（悲しい目＋大きく開いた口）。表情ごとに口の開き量を制限する係数で緩和する
- **B. 表情遷移のクロスフェード** — 投影済みテクスチャ間を補間する。実装コストは低い
- **C. 自動まばたき・アイドル揺れ** — `blink` テクスチャをランダム間隔で差し込む。頭・体の微小な揺れを手続き的に足す
- **D. 外部生成画像のインポート導線** — **優先度高。T2の結果次第では T2 の直後に着手する。** 投影前の1024px画像を外部で作って持ち込めるようにする。**製品はクラウドを呼ばないまま品質問題を解決できる出口**（[SPEC.md](../SPEC.md) 4.10 D、4.7.3 段階7）。中立キャプチャの書き出し、投入画像の位置ずれ・左右反転・色差の検出と警告、キャッシュ署名への反映まで含む
