# PicoVTuberのコネクタを変更する

## 設計

1. `AGENTS.md`の「コネクタ開発ルール」と「エラー処理・リソース」、`SPEC.md`の第2章・第3章を読む。
2. 生成工程なら`src-tauri/src/pipeline/stages/`、配信出力なら`src-tauri/src/studio/outputs/`の既存実装を検索し、類似コネクタを拡張できない場合だけ新設する。
3. 外部副作用、ユーザー由来パス、共有状態、子プロセス、GPU依存、キャンセル時解放を先に列挙する。
4. **クラウド推論を持ち込まない。** 外部の生成API・ASR・TTSを呼ぶ設計は採らない。必要な処理はローカルランタイム（`pipeline::runtime`）へ委譲する。

## 実装

1. `Stage`または`Output`トレイトと`inventory::submit!`で自動登録し、中央の手動一覧を増やさない。ファイル名は英小文字・数字・アンダースコアだけにする。
2. 生成工程は依存を`requires()`／`produces()`で申告する。**実行順を配列で直書きしない**（`pipeline::plan()`が申告から順序を決める）。同じ成果物を2つの工程が名乗らない。
3. 生成工程は入力を破壊しない。受け取った成果物を上書きせず、自分の出力を新しいファイルとして`ctx.job_dir`の下へ置く。これで「その工程から後ろだけ」の再実行が成立する。
4. 配信出力の`start()`／`stop()`は冪等にする。二重起動・二重停止で失敗させない。使えない環境では`availability()`が理由付きで未対応を返し、`start()`が黙って何もしない状態を作らない。
5. 設定が必要なら`add-picovtuber-setting`も使い、`config_schema()`と実行時`cfg.get()`へ接続する。値をフィールドへ固定しない。
6. ユーザーパスは`permissions`、外部プロセスは`tools::process`、文字列は`text`、状態更新は`store`の共通層を使う。独自の許可判定、直接起動、直接上書きを作らない。
7. 失敗は`Result`で伝播する。**欠損を白紙や複製で埋めて成功に見せない。** 許可したフォールバックだけ理由コメントを付ける。
8. 正常、失敗、キャンセルの全経路でプロセス、接続、音声ストリーム、タイマー、リスナ、オブジェクトURL、GPUリソースを解放する。長い処理は`ctx.cancel`を定期的に見る。

## 検証

1. 正常系に加え、未設定、重み未取得、GPUなし、タイムアウト、権限外、破損状態、並列呼び出し、キャンセルをテストする。
2. 関係する設計ガードを`guard_scan`共通走査で追加または更新する。ガードの例外で実装ミスを隠さない。
3. `SPEC.md`の工程分類表またはインターフェース定義、`docs/SETTINGS.md`、必要なら`README.md`と`MANUAL.md`を同期する。工程を足して分類表へ載せ忘れると`doc_sync::guard`が落ちる。
4. `cargo check`、関係する単体テスト、設計ガード、`git diff --check`を通す。依存変更時は対象lockfileを`cargo audit`する。
