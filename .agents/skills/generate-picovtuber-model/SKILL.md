# PicoVTuberのモデル生成を行う

工程の正本は`SPEC.md`の工程分類表と`src-tauri/src/pipeline/stages/`。**会話履歴から個別コマンドを組み直さず、この手順を使う。**

## 前提を確認する

1. `AGENTS.md`と`SPEC.md`の第2章を読む。
2. 入力イラストが`MANUAL.md`の条件（全身・正面直立・背景透過または単色・長辺1024px以上）を満たすか確認する。満たさない絵で工程を回して「品質が出ない」と結論しない。
3. **権利を確認する。** 利用者が権利を持つ、または許諾を得た画像であることを確認できない素材で生成を進めない。
4. ML工程を使うなら Python ランタイムと重みが揃っていることを確認する。`cargo xtask setup runtime` / `setup models` は**まだ自動取得を有効にしていない**（採用モデルとライセンスの確定待ち。docs/TASKS.md）。いまは手元に置いたものを `PICOVTUBER_RUNTIME_PYTHON` と `PICOVTUBER_MODELS_DIR` で指す。GPU種別も確認し、CPUしか無い環境でGPU前提の所要時間を見積もらない。

## 生成する

1. 正規入口は生成ウィザード（`ui/wizard.html`）だけ。工程スクリプトを個別に手で叩いて順序を組み直さない。CLI からの一括生成はまだ用意していない。
2. 工程は`preprocess` → `segment` → `multiview` → `mesh` → `rig` → `expression` → `viseme` → `pack` の順に走る。順序は`requires()`の申告から決まるので、順序を変えたいときは申告を直す。
3. 中断しても`app_data_dir/jobs/<ジョブID>/job.json`に完了工程が残る。再開は同じジョブIDを指定する。**`job.json`の記録だけを信じず、成果物の実在と検証を通ったものだけを完了扱いにする。**
4. ある工程からやり直す場合は、その工程の出力フォルダを消してから再開する。前の工程の出力は消さない（入力を壊さない原則）。

## 品質を検証する

1. **工程が最後まで通ったことを品質の合格にしない。** 次を実際に見る。
   - 側面・背面が正面の複製や白紙になっていないか
   - メッシュの輪郭が入力イラストのシルエットと一致するか
   - テクスチャの寸法が入力の等倍以下か（**引き伸ばし拡大は禁止**）
   - humanoidボーンが全て入っているか、関節位置が体格に合っているか
   - 表情5種と口形6種が実際に形として違うか（名前だけ違って同じ形になっていないか）
2. 透過の確認は四隅のアルファ値だけで済ませず、透過市松または配信ソフトの実画面で見る。
3. 生成に失敗した工程は、白紙や複製で埋めずに失敗として扱う。埋めた成果物を「できた」と報告しない。

## 工程の入出力契約を変える場合

1. `SPEC.md`の工程分類表と成果物の命名規約を先に更新し、`Stage`の`requires()`／`produces()`を合わせる。
2. `scripts/`のスクリプトのCLI引数と出力形式を同じPRで同期する。
3. `doc_sync::guard`と`pipeline::guard`を通す。工程を足して分類表へ載せ忘れると落ちる。

## 停止条件

- 入力画像の権利を確認できない。
- 採用する生成モデルのライセンス・再配布条件が不明。
- 重みが未取得のまま「動いた」と報告しようとしている。
- 欠損を複製や白紙で埋めた成果物を成功として扱おうとしている。
